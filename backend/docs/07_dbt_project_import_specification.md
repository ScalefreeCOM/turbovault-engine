# dbt Project Import — Specification

**Status:** Draft 1, 2026-11-13 (Phase 0). Decisions recorded in §2.
**Tracking:** `product_development_milestones` #460 (import) and its phase sub-issues; related #442
(per-model output attributes) and #461 (custom models). The issue texts were initial ideas; this
document supersedes them where they differ.
**Studio:** every change this initiative makes to the Engine's model or behaviour is documented in
[`STUDIO_INTEGRATION_NOTES.md`](STUDIO_INTEGRATION_NOTES.md), the single handover document for the
Studio team.

---

## 1. Summary

Teams with an existing **datavault4dbt** project can import it into a TurboVault project from its dbt
artifacts. The import rebuilds the Data Vault model (sources, stages, Hubs, Links, Satellites, PITs,
reference tables, snapshot controls), keeps the models upstream of the stages as pre-stages, and keeps
each model's name, path and configuration, so that generating the project again produces (almost) the
same dbt project. Models the import can't map are reported; keeping them as custom models comes later
and is optional.

The import never runs dbt, never connects to a warehouse and never accesses the network: it only reads
artifact files. AutomateDV projects are out of scope for now, but the design keeps the
package-specific part separate so an AutomateDV adapter can be added.

## 3. Inputs

| File | Required | Used for |
|------|----------|----------|
| `manifest.json` | yes | Models (`raw_code`, `config`, `unrendered_config`, `original_file_path`, `alias`, `schema`, `database`, `tags`, `description`, `columns`, `meta`, `depends_on`), sources, project macros, lineage (`parent_map`, `child_map`), `metadata` (`dbt_schema_version`, `dbt_version`, `adapter_type`, `project_name`). |
| `catalog.json` | no | Column data types of sources and models, as the warehouse reports them. Without it, types come from the YAML `data_type` and the report warns. |
| `dbt_project.yml` | no | `vars` (the manifest has none): values for `var()` calls and the datavault4dbt settings (hash algorithm, column aliases, …). Folder-level `+schema` / `+materialized`. Project name. |
| `packages.yml`, `dependencies.yml`, `package-lock.yml` | no | datavault4dbt version, where argument formats differ between 1.x and 2.x. Detecting other DV packages. |
| `profiles.yml` | never | Contains credentials. |

Accepted as single files or as a directory holding `target/manifest.json` (+ `target/catalog.json`) and
`dbt_project.yml`. `metadata.dbt_schema_version` must be v12; anything else stops the import with
`dbt.unsupported_manifest_version`. Fusion manifests (`dbt_version` 2.x) have the same structure for
every field the import reads (verified on a Fusion 2.0.1 manifest).

Not imported, but counted in the report: seeds (their data isn't in the manifest), dbt snapshots, tests,
analyses, exposures, semantic models, Python models.

## 4. Architecture

```
manifest / catalog / dbt_project.yml / packages
   1  Read        load, check the version, index the parts needed (nodes, sources, macros, lineage)
   2  Extract     render each model's Jinja in a sandbox; record every package macro call (§6)
   3  Normalize   package adapter (datavault4dbt): argument formats of 1.x / 2.x -> neutral DV description
   4  Map         neutral description -> import DomainModel; trace stage columns to source columns (§7)
   5  Report      per model: imported / imported with changes / skipped, with reasons (§11)
   6  Plan, Execute   the existing import pipeline: merge / replace_all / update_only, dry run, change report
```

- Code lives in `engine/services/imports/dbt/`: `artifacts.py` (reading, versions), `extract.py`
  (sandbox), `adapters/datavault4dbt.py` (normalization, signature table), `mapping.py`,
  `naming.py` (convention inference), `codes`.
- A new import source `DbtSource` (`manifest`, optional `catalog`, `dbt_project`, `packages`) joins the
  `SourceInput` union. The CLI gets `--format`, and detects a manifest by `metadata.dbt_schema_version`
  before falling back to the JSON or IRiS import.
- **Warnings and skips for direct parsers.** Only the Excel/SQLite path can report non-fatal issues
  today; the parser contract gains a way to return issues and skipped entities with the domain model.
- **Issue locations** gain the dbt node id and file path.
- Steps 1, 2, 4 and 5 don't depend on the package. An AutomateDV adapter would replace step 3 only.

## 5. Example corpus (Phase 1)

Five projects were profiled with `scripts/dbt_import/profile_manifest.py`, and their calls extracted with
the prototype `scripts/dbt_import/capture_calls.py`. Four are internal (anonymised here), one is TurboVault's
own TPC-H output.

| Project | dbt | Warehouse | Data Vault models | Other models | Stages read |
|---------|-----|-----------|-------------------|--------------|-------------|
| A | dbt Cloud | Snowflake | 34 | 0 | sources |
| B | dbt Cloud | Snowflake | 38 | 1 downstream | sources |
| C | dbt Fusion 2.0.1 | Snowflake | 58 | 13 downstream, 2 unrelated | seeds |
| D | dbt Core 1.10 | BigQuery | 1,027 | 97 upstream (views), 64 downstream, 8 unrelated | upstream models |
| TPC-H | dbt Core 1.12 | Postgres | 59 | 2 pre-stages | sources, pre-stages |

**The prototype extracted every datavault4dbt call: all 1,224 models, no failure.** Render errors only
occurred in models without a Data Vault call (they call project macros or other packages); the import
stores those verbatim and never needs to render them.

Findings that shape this specification:

- **Notations differ within one project.** D mixes `yaml_metadata` blocks (~145 models), YAML parsed
  with `fromyaml` and passed parameter by parameter (~880) and `set` variables (2). A uses `fromyaml`
  throughout, B and C `yaml_metadata`.
- **Values, not the code, decide.** Many `fromyaml`-style calls pass `missing_columns=…` or
  `derived_columns=…` that turn out empty. Rendering the Jinja is the only reliable way to know.
- **Stages read upstream models** in D (all 86 stages) and seeds in C. Importing pre-stages under their
  original names is essential.
- **Derived columns, missing columns, `sequence` and `enable_ghost_records`** are unused in the examples:
  the upstream models do that work. Prejoins: 2 stages, both onto models, one in each notation.
- **Per-entity settings occur:** `ledts_alias` on 335 v1 Satellites (mostly the default, some
  `loadenddate` / `valid_to`), Satellites renaming their hashdiff (`src_hashdiff: {source_column, alias}`,
  18), Hubs loading a differently named hashkey column (`hk_column`, 8), `add_is_current_flag: false` (1),
  `is_active_alias` (1), PIT `custom_rsrc` (6).
- **Quirks:** YAML blocks with SQL-style comment lines (`-- multi_active_config:` becomes a key);
  parameters datavault4dbt ignores (`ldts` / `rsrc` on Hubs and Satellites, where the parameter is
  `src_ldts` / `src_rsrc`).
- JSON metadata blocks, wrapper macros around datavault4dbt calls and `var()` calls don't occur in the
  examples; synthetic fixtures cover them.

## 6. Extracting the calls

### 6.1 Sandbox rendering

Every model's `raw_code` is rendered in a `jinja2.sandbox.SandboxedEnvironment` that imitates dbt at
parse time. Package macros don't run; they record their arguments:

| Name | Behaviour |
|------|-----------|
| `datavault4dbt.<macro>(…)`, other DV packages | record package, macro, positional and keyword arguments |
| `config(…)`, `config.get()` | record the configuration set in the model |
| `ref(name)`, `ref(package, name)` | a marker naming the model |
| `source(source, table)` | a marker naming the source table |
| `var(name, default)` | `dbt_project.yml` vars, else the default, else an *unresolved* marker (warning) |
| `env_var(name, default)` | the default, else an *unresolved* marker. Never the real environment. |
| `fromyaml`, `fromjson`, `toyaml`, `tojson` | `yaml.safe_load` / `json` |
| `is_incremental()` → False, `execute` → False, `this`, `target`, `adapter`, `run_query`, `log`, `exceptions` | inert stand-ins; `raise_compiler_error` marks the model as failed |
| any other name or call | an *unresolved* marker instead of an error (project macros, other packages) |

Undefined values (e.g. `metadata_dict['missing_columns']` for a key the YAML lacks) become "not set",
as in dbt. Unresolved markers in a parameter that matters are reported on that parameter
(`dbt.value_unresolved`), not on the whole model.

### 6.2 Notations

All of these produce the same recorded call:

```jinja
{# 1. yaml_metadata block, passed as a whole (current standard) #}
{%- set yaml_metadata -%}
hashkey: hk_customer_h
business_keys: [customer_id]
source_models: stg_customer
{%- endset -%}
{{ datavault4dbt.hub(yaml_metadata=yaml_metadata) }}

{# 2. YAML block parsed with fromyaml, parameters passed one by one (older) #}
{%- set metadata_dict = fromyaml(yaml_metadata) -%}
{{ datavault4dbt.hub(hashkey=metadata_dict['hashkey'],
                     business_keys=metadata_dict['business_keys'],
                     source_models=metadata_dict['source_models']) }}

{# 3. JSON block parsed with fromjson #}
{%- set metadata_json -%} {"hashkey": "hk_customer_h", ...} {%- endset -%}
{%- set metadata = fromjson(metadata_json) -%}
{{ datavault4dbt.hub(hashkey=metadata.hashkey, ...) }}

{# 4. set variables #}
{%- set hashkey = 'hk_customer_h' -%}
{{ datavault4dbt.hub(hashkey=hashkey, business_keys=['customer_id'], source_models='stg_customer') }}

{# 5. literals in the call #}
{{ datavault4dbt.hub(hashkey='hk_customer_h', business_keys=['customer_id'], source_models='stg_customer') }}
```

Mixed forms are fine (a `yaml_metadata` block plus separate parameters). Wrapper macros (a project macro
that calls datavault4dbt) are supported by loading the root project's macros from the manifest into the
sandbox (Phase 2, behind a fallback: unknown wrappers are reported).

### 6.3 Resolving `yaml_metadata` like datavault4dbt

datavault4dbt's `yaml_metadata_parser` decides each parameter: a key in the YAML wins over a separately
passed value; otherwise the separate value applies (`false` counts, none doesn't) or the default. The
import applies exactly this rule, and reports a parameter given both ways (`dbt.parameter_given_twice`,
info).

### 6.4 Normalizing arguments

The datavault4dbt adapter turns every accepted argument format into one shape, following what the
macros themselves accept, per version (a signature table generated from the datavault4dbt sources of
the supported 1.x and 2.x releases):

- `source_models`: a model name, a list of names, a list of `{name, …}` dicts, or a dict of
  `{model: {…}}` → a list of `{model, bk_columns / fk_columns, rsrc_static, hk_column, link_hk, …}`.
- `business_keys`, `foreign_hashkeys`, `src_payload`, `ma_attribute`: a string or a list → a list.
- `prejoined_columns`: the dictionary notation (≤ 1.x) or the list notation → the list notation.
- `src_hashdiff`: a column name or `{source_column, alias}`.
- `source_model` of a stage: `{source: table}` (dbt source) or a model name (`ref`).

Keys a macro doesn't know are reported as ignored (`dbt.parameter_ignored`, info) and dropped. That
includes YAML lines that are SQL comments and parameters datavault4dbt silently ignores.

### 6.5 Security and limits

Manifests are untrusted. The sandbox blocks unsafe attribute access; templates get no loader, no file,
network or environment access; YAML is loaded with `safe_load`; ranges are bounded by the sandbox.
Manifest size and render time per model are limited and documented (Phase 7 measures them; D is
15 MB / 3,000 nodes).

## 7. Mapping

### 7.1 Sources

Each dbt source (`source_name`) becomes a source system (schema, database, description), each source
table a source table (`identifier` or `name`, description), with columns and types from the catalog,
else the YAML. Only sources a stage or a pre-stage reads are imported. When every table of a system
shares the record source or load date, it is set on the system (value inheritance).

### 7.2 Pre-stages (models upstream of the stages)

- A model without a Data Vault call that a stage reads (directly or through other models) becomes a
  **pre-stage**: a source table of type `prestage` whose SQL is the model's `raw_code`, under its
  original model name (§9.1), in the source system of what it reads.
- Chains of upstream models are pre-stages reading each other with `ref()`.
- A stage reading a **seed**, a **dbt snapshot** or a **model of another package/project** gets a
  pre-stage without SQL (maintained outside TurboVault) under that name. Seed data stays in the repo.
- Columns: the catalog's columns of the model, else its YAML columns.
- The ephemeral check (`validate.prestage.ephemeral`) applies only to pre-stages a stage reads; models
  only other pre-stages read may be ephemeral (change to the pre-stage feature).

### 7.3 Stages

| Stage parameter | Becomes |
|-----------------|---------|
| `source_model` | the source table (dbt source) or pre-stage (model) the stage belongs to |
| `ldts`, `rsrc` | the table's load date / record source (TurboVault reads them like datavault4dbt) |
| `hashed_columns` | hash keys and hash diffs: matched to Hubs / Links / Satellites by name (§7.5) |
| `derived_columns` | derived columns, including ones that shadow a source column (§9.4) |
| `prejoined_columns` | prejoins; the target is a source table or a pre-stage (`ref_model`) |
| `multi_active_config` | the multi-active keys of the Satellite loaded from the stage |
| `missing_columns`, `include_source_columns`, `sequence`, `enable_ghost_records` | stage options (§9.3) |

**Tracing a stage column to its origin.** A Hub, Link or Satellite column in TurboVault maps a source
column, a prejoined column or a derived column. A stage column is a prejoined column if a prejoin extracts
it, a derived column if `derived_columns` defines it (also when it shadows a source column), else a column
of the stage's source table or pre-stage. Columns the catalog doesn't know are created (type empty,
warning).

### 7.4 Data Vault entities

| Macro | TurboVault |
|-------|------------|
| `hub`, `ref_hub` | Hub (standard / reference), columns, source mappings per stage |
| `link`, `nh_link` | Link (standard / non-historized), Hub references, payload |
| `sat_v0`, `ma_sat_v0`, `nh_sat`, `ref_sat_v0` | Satellite (standard / multi-active / non-historized / reference) |
| `sat_v1`, `ma_sat_v1`, `ref_sat_v1` | the v1 view of the Satellite: name and options (§9.5) |
| `eff_sat_v0` | effectivity Satellite of the Hub (`create_effectivity_satellite`) |
| `rec_track_sat` | record-tracking Satellite of the Hub or Link |
| `pit` | PIT |
| `ref_table` | reference table |
| `control_snap_v0`, `control_snap_v1` | snapshot control table and its logic |

### 7.5 Resolving relationships

- **Hub ↔ stage:** a Hub's `source_models` name stages; per stage, `bk_columns` (default: the Hub's
  business keys) map the Hub's columns.
- **Link → Hubs:** each foreign hash key is matched to a Hub by name. An aliased foreign hash key (a
  second reference to the same Hub, e.g. a self-link) is matched by comparing the business key columns
  the stage hashes into it with the Hub's business keys; it becomes a Hub reference with an alias.
  Ambiguity is reported (`dbt.link_hub_ambiguous`) and the Link skipped.
- **Satellite → parent:** `parent_hashkey` and the Satellite's stage identify the Hub or Link.
- **v1 → v0:** `sat_v0` names the v0 model; the pair confirms the Satellite's v0/v1 names.
- **PIT:** `tracked_entity`, `sat_names` (v1 names) and `snapshot_relation` resolve to the Hub/Link,
  Satellites and snapshot control.
- **Reference table:** `ref_hub` and `ref_satellites` (with include / exclude columns).

### 7.6 Groups, descriptions and tags

- A subject area (group) comes from the model's folder below its layer folder, else from a tag that isn't
  a layer tag. Folders and tags stay in the output attributes either way.
- Descriptions of sources, columns and models are imported. Tests are not (TurboVault generates its own).
- Tags and other configs are kept in the output attributes (§9.1).

## 8. Naming conventions

Names are kept as they are (D3). Inference only sets the project's **default patterns**, so that new
entities follow the project's style:

- Hash keys (`hashkey_naming`), hash diffs (`hashdiff_naming`), v0/v1 Satellites
  (`satellite_v0_naming` / `satellite_v1_naming`), effectivity and record-tracking Satellites, stages and
  pre-stages (new patterns, §9.1).
- A pattern is set only when most entities of a kind follow it (threshold to be tuned on the corpus); the
  report shows each inferred pattern with how many names match, and the names that don't keep their own
  name (per-model output attribute or per-entity field).

## 9. TurboVault metadata extensions

What the import needs and TurboVault lacks today. Each lands with its Studio notes.

### 9.1 Model output attributes (#442)

One record per generated dbt model, keyed by entity and output kind:

| Entity | Output kinds |
|--------|--------------|
| source table | `stage`, `prestage` |
| Hub | `hub`, `effectivity_satellite`, `record_tracking_satellite` |
| Link | `link`, `record_tracking_satellite` |
| Satellite | `v0`, `v1` |
| PIT, reference table | `pit`, `reference_table` |
| snapshot control | `v0`, `v1` |

Fields (all optional; empty means "derived as today"): `model_name`, `alias`, `file_path` (relative to
`models/`), `schema`, `database`, `materialized`, `tags`, `config` (other config keys verbatim: hooks,
`unique_key`, …). Proposed storage: one table with explicit nullable foreign keys to the entities (as
`StagingColumn` does), unique per entity and output kind, and per project by model name.

Generation resolves every model name through one service, so file names **and every reference**
(stage names in `source_models`, v0 in v1, v1 in PITs and reference tables, snapshot controls in PITs,
pre-stages in stages and prejoins) follow the stored names. That also fixes the hard-coded `_v0` / `_v1`
references #442 lists. New project patterns for stage and pre-stage names replace the hard-coded
`stg__…` / `pstg__…`. A generation option (`use_original_paths`, default on) switches back to the
standard structure. Folders outside the standard layer folders get their schema and materialization from
the attributes.

### 9.2 Hash diff name and alias (Satellite)

- `hashdiff_name`: the stage's hash diff column (default: the project's `hashdiff_naming` pattern).
- `hashdiff_alias`: the column name inside the Satellite when it differs (`src_hashdiff: {source_column,
  alias}`), e.g. one uniform `hashdiff` column in every Satellite.

### 9.3 Stage options

Project defaults (configuration) and per source table overrides:

| Option | Default | Per table | Notes |
|--------|---------|-----------|-------|
| `include_source_columns` | true | yes | |
| `enable_ghost_records` | true | yes | |
| `sequence` | none | yes | a column name |
| missing columns | — | yes | proposed as source columns flagged `is_missing` (name + type): the stage adds them as NULL columns, and they can be mapped like other columns |

Per-model load-date / record-source columns (`src_ldts`, `src_rsrc`) stay out for now (lenient).

### 9.4 Derived columns that shadow a source column

A derived column may take the name of a source column of its table: the stage computes it in place of
the source column (datavault4dbt's behaviour). Mappings then use the derived column. A Hub/Link column
transformation on the same column conflicts and fails validation. Replaces today's rule that a derived
column's name must be new (breaking change allowed, D8).

### 9.5 Satellite v1 options

Per Satellite: `v1_ledts_alias` (default: the project's datavault4dbt `ledts_alias`),
`v1_add_is_current_flag` (default true, as generated today), `v1_include_payload` (default true), and
whether the Satellite gets a v1 at all (default: the project's `generate_satellite_v1_views`).

### 9.6 Smaller additions

- Effectivity Satellite `is_active_alias` per Hub.
- PIT `custom_rsrc`: generation writes the stored `custom_record_source`.
- Hub loaded from a differently named hash key column of a stage (`hk_column`): role-playing sources
  (e.g. author / committer users from one stage). Data model designed in Phase 3.
- Snapshot control: generation writes the stored `snapshot_end_date` (`end_date`) and an `sdts_alias`
  when set.

## 11. Report

Every issue carries the model's node id, file path, the parameter it concerns and a stable code.
Proposed codes (final list in `services/imports/codes.md`):

| Code | Severity | When |
|------|----------|------|
| `dbt.unsupported_manifest_version` | error (abort) | manifest isn't v12 |
| `dbt.model_not_mapped` | info | model without a Data Vault call that no stage reads (custom model candidate) |
| `dbt.model_render_failed` | error (model skipped) | the model's Jinja can't be rendered |
| `dbt.macro_unsupported` | error (model skipped) | a datavault4dbt macro the import doesn't support |
| `dbt.parameter_unsupported` | warning | a parameter imported leniently (dropped) |
| `dbt.parameter_ignored` | info | a parameter datavault4dbt itself ignores |
| `dbt.parameter_given_twice` | info | given in `yaml_metadata` and separately |
| `dbt.value_unresolved` | warning | `var()` / `env_var()` / unknown function without a value |
| `dbt.reference_unresolved` | error (entity skipped) | a stage, parent or Satellite that isn't in the project |
| `dbt.link_hub_ambiguous` | error (Link skipped) | a foreign hash key matches no Hub, or several |
| `dbt.catalog_missing` | warning | no catalog: column types from YAML only |
| `dbt.naming_inferred` | info | a naming pattern was inferred, with its share of matching names |

The report also lists node counts per resource type (seeds, tests, … not imported).

## 12. Testing

1. **Round trip on TurboVault's output:** generate projects covering every entity type, non-default
   naming and template overrides; `dbt parse` them (dev dependency or an opt-in CI job); import the
   manifest into an empty project; compare the JSON exports, ignoring ids and fields dbt output can't
   carry.
2. **Synthetic manifests:** one per notation (§6.2), argument format (§6.4), quirk and error case.
3. **Internal examples (opt-in):** the corpus folder outside the repository; tests skip when it is
   absent. Never committed (D1).
4. **Regenerate and compare:** import, generate, `dbt parse` the result and compare both manifests on what
   matters: model names and paths, references, macro arguments.
5. Re-importing the same artifacts writes nothing; a dry run changes nothing.
